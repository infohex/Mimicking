Mimicking: one person's words, spoken live in another person's voice

The content, tone and rhythm of the speech stay the original speaker's; the voice the audience hears is the one you choose. All it needs is a few seconds of that person's recording, with no training. It runs on an ordinary server with a graphics card, and it is our own version, reimplemented in the Rust language and made substantially faster.

What problem it solves

Nearly every "zero-shot voice conversion" model on the market that sounds good is research code: written in Python, able to carry only one or two streams per graphics card, and needing a full development environment installed on the server. What we did was take the best-sounding one of them (the public Seed-VC model) and reimplement it on the same mathematical principles, making it four times faster, able to serve more people at the same time, and turning it into a standalone program that can be copied straight onto a server and run. The model's "knowledge" (the weights) is the publicly released version; we did not retrain, so it sounds the same as the original.

How it works

Why it is four times faster

The original is slow not because the graphics card cannot keep up, but because the card spends most of its time waiting for instructions. For every pass, Python has to hand the card more than two thousand tiny instructions; the card executes each one in a few microseconds, but waits longer for the next instruction than it spends executing. We did three things:

1. Record the instructions as a "macro"

The full set of instructions for one pass is recorded only once; afterwards it is replayed as a whole every 0.25 seconds, and the card no longer waits on anyone.

2. Merge the tiny instructions

We rewrote the order of computation in the core network using the same mathematics, merging more than two thousand instructions into fewer than two hundred. Same result, half the time.

3. Everything around it in Rust

The "manual work" of cutting audio into blocks, stitching, resampling and silence detection no longer goes through Python: stable, predictable, and easy to package as a standalone program.

The figures are measurements of the same speech sample on the same machine (NVIDIA RTX A4000 graphics card, 16 GB, compute in the same class as an RTX 3070); the original is the public code in real-time mode.

How far it scales

"Steps" is how finely the voice is "developed". The standard tier of 10 steps sounds best; 6 steps sounds slightly rougher, but the same compute carries one more stream.

Latency: a tier that must be chosen in advance

How much later the audience hears the converted voice than the speaker opens their mouth depends on one setting: how much further ahead the system listens before it starts to "re-speak". Listening further ahead makes the transitions more natural; listening less makes the response faster. The original offers the same choice. We exported two model sets; pick one at deployment:

Low-latency tier (listens 0.02 s ahead): about 0.6 s overall.

Quality-first tier (listens 2 s ahead): about 2.5 s overall.

Neither timeline includes the latency of the headphones or sound card themselves (wired about 0.03 s, Bluetooth headsets commonly 0.15 to 0.25 s). The low-latency tier is close to video-conferencing level and can be used for two-way conversation; the quality-first tier suits one-way scenarios (announcements, dubbing, live streaming, converting one party's voice and sending it to the other). Values between the two tiers are also possible; changing tier only means re-exporting a model set, which takes minutes and needs no retraining.

Integration is the simplest possible "feed one block in, take one block out"; any system that can send audio cut into timed blocks can connect: telephony gateways, conferencing services, live-stream ingest. The requirement is a Windows server with an NVIDIA graphics card (we measured the figures above on an RTX A4000, which is in the same class as an RTX 3070; several cards run in parallel and the stream counts add up per card; higher-end cards carry more streams). The folder is about 3 GB, most of it graphics-card runtime libraries and models.

Boundaries and risks, stated up front

HardwareOnly NVIDIA graphics cards are supported at present. Other cards would need a separate runtime backend; technically feasible but not done.
LatencyTwo tiers to choose from: low-latency about 0.6 s, quality-first about 2.5 s, see above. Choose per scenario at integration time.
Voice sourceThe voice is determined entirely by the reference recording; the recording's pitch and sense of age carry over. The reference recording must be clear, with no background music.
Model licenceThe model weights come from a public release licensed under GPL-3.0; our program code is our own implementation and contains no original code. Before external commercial use, the licence of the model weights needs a legal review, or self-trained weights should be used instead.
LanguageThe model only cares about "what sounds were spoken" and does not depend on the specific language; Chinese and English both work. Uncommon languages have not been systematically evaluated.

Frequently asked questions

Does each target voice need separate training?

No. Given a clear recording of 3 seconds or more, it "memorises" the voice within a few hundred milliseconds, and voices can be switched at any time during a call.

Will it change what is said?

No. It only changes the voice; the words, speaking rate, pauses and emotional contour are all kept. It does not translate and does not understand meaning.

What about when nobody is speaking?

There is silence detection: when it is quiet, the output is quiet too; it does not produce sound "out of nothing".

How is 4 streams per card worked out?

The streams on one card are processed one after another, and each stream has to wait for the whole round to finish before it sounds, so the round time counts directly towards every stream's latency. In the quality-first tier each stream takes about 50 ms per block, so 4 streams make a 200 ms round, within the 240 ms cadence; in the low-latency tier each stream takes about 28 ms, so 4 streams make a 115 ms round, with more margin and more stability. Adding streams brings a round close to or past the cadence: latency doubles and any jitter drops blocks, so the cap is set at 4 streams. The measured card is an RTX A4000 (16 GB, in the same class as an RTX 3070); two cards with 4 streams each take about 120 ms per round per card. The stream count scales linearly with graphics-card performance; use the estimator above.

Does quality suffer compared with the original?

No. We use the same model knowledge and only rewrote how it executes. Objective scores are level with or slightly above the original, and the stage-by-stage numerical comparison matches.

Can it be as delay-free as talking face to face?

Completely imperceptible is not possible: the system has to collect at least a short stretch of speech before processing it. The low-latency tier is about 0.6 s overall, comparable to video conferencing and usable for two-way conversation; the quality-first tier is about 2.5 s and suits one-way scenarios only. A compromise between the two tiers can be chosen as needed.

Is deployment complicated?

Place a folder of about 3 GB on a Windows server with an NVIDIA graphics card and it runs; the bundled check command verifies the integrity of the model files.
