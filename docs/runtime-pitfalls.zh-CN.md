# 运行时的坑与规则

在 ONNX Runtime + CUDA 上做多会话、多线程、多卡时踩过的坑，以及由此定下的规则。库里能兜底的已经兜底（标"库已处理"），
其余是使用方（测试台、未来的任何集成）必须遵守的。来源：2026-10-26/27 在 MimickingLab 上做实时与多卡时的实测。

## 1. ONNX Runtime 每个进程只能有一个环境 —— 库已处理

- 现象：第二次 `ort::init_from(...)` 报 `only one environment is allowed per process`。测试台里"换模型要重启"就是它。
- 规则：进程内只创建一次运行库。`OnnxRuntime::load` 现在第一次创建、之后每次都返回同一个环境（忽略新传入的 dll 路径）；
  换设备、重载、再开一个池都用 `rt.clone().with_device(...)`。
- 推论：onnxruntime.dll 的路径只在第一次加载时有效，换路径必须重启进程。

## 2. CUDA Graph 录制不能和进程里任何别的 CUDA 调用并发 —— 库已处理（加载期）

- 现象：两张卡同时加载时报 `CUDA failure 901: operation failed due to a previous error during capture`，
  在 Gelu/Erf 等任意节点上。一个线程在 `cudaStreamBeginCapture` 期间，另一个线程做 cudaMalloc、同步 cudaMemcpy
  等"非捕获安全"调用，会让录制失效并连带报错；**不同的卡也一样**，因为判断是进程级的。
- 规则：`BoundGraph::load` 和 `warm_up`（第二次 run 即录制）持有进程级 `CAPTURE_LOCK`，多线程同时加载会自动排队。
- 使用方仍须遵守：**先把所有模型加载完，再开始实时推理**；不要在别的线程正在跑图时加载新模型（跑图时的主机↔设备拷贝
  会落在录制窗口里）。测试台加载新池前先停掉所有会话、卸掉旧池，就是为了这个。
- 回放（`run_binding` 复用已录制的图）在多线程里并发是安全的，因为回放不录制。

## 3. 一次 run 是同步调用：一张卡一个线程

- `Session::run` 阻塞到结果出来。一个线程轮询多张卡，各卡只会轮流干活，不会同时干活。
- 规则：每个设备一个工作线程、一套 `Runner`（`Stages` 绑定在加载时的设备上）；会话（`Session`，无模型）按
  `r % G` 分到各卡；调度线程广播一块、收齐结果。测试台的 `pool.rs` 是参考实现。
- `BoundGraph` 的设备常驻缓冲属于它所在的线程，不要跨线程共用一个 `Runner`。

## 4. ORT 线程池默认自旋 —— 库已处理

- 现象：七张图各一个线程池，空闲时仍在自旋，CPU 白耗，和音频线程抢核。
- 规则：`session.intra_op.allow_spinning = 0`、`inter_op` 同样，intra 线程 2 个（CUDA EP 下 CPU 侧几乎没有算子）。

## 5. 静态形状：参数不能运行时改

- 块长、右前瞻、提示长度决定每张图的形状；改任何一个都要重新导出一套图（约 2 分钟），放在独立目录，目录的
  `manifest.json` 记录配置，`ModelFiles::config()` 读回。使用方按目录加载，不要再在代码里写死几何。
- 唯一动态形状的图是 CAM++（参考长度可变），它**不能开 CUDA Graph**（形状算子会落到 CPU EP）。而且它的卷积在 ORT CUDA EP
  里以 cuDNN fallback 模式运行，一次约 0.2 s（约 25× 实时），这就是"参考提示约 350 ms"的大头；批量算嵌入（训练缓存）
  用 PyTorch 版（150× 实时）。要提速推理端可按参考长度分桶导出几张静态图。

## 6. 单路时 GPU 会降频

- 一路每 240 ms 只忙约 30–50 ms，A4000 会从 2100 MHz 掉到 630 MHz，块耗时 p50 上升 1.5–2 倍、p95 出现尖峰。
  多路并发（GPU 不空闲）或锁频（`nvidia-smi -i N -lgc 1800,1800`，管理员）可消除。评估单路延迟时要知道这一点。

## 7. 不要在推理线程上做慢活

- 质量探针（CAM++ 嵌入 10 s 音频，100–500 ms）、文件 IO、导出子进程都放自己的线程。引擎线程每停顿一次，
  输入积压、扬声器欠载、延迟上爬一级。

## 8. 门控决策要对齐到它所属的输出块

- 右前瞻 2.0 s 时，此刻的输出对应 2 秒前的输入；用"此刻"的 VAD 决策去门控它会把话切碎。`Session` 已按算法延迟排队
  决策（库已处理），自定义 VAD 实现时同样要注意：决策的时间轴是输入，门控的时间轴是输出。

## 9. 音频设备侧

- WASAPI 采集的"数据不连续"标记可能来自设备本身（某些 USB 麦克风每几秒一次，不加载模型也有），PortAudio 不报告它；
  计数即可，不要逐条打日志（控制台写入会反过来拖慢采集线程）。
- 扬声器队列需要控制器：生产与消费平均相等，队列只在"出事"时单向漂移；按目标余量补静音/丢输入，死区内不动。

## 10. 码本模型的调节器统计量要冻结（2.0，2026-10-31）

- 长度调节器是 Conv3 + GroupNorm(1, d)，统计量取自它拿到的整段。2.0 的码本输出近乎常量（第一层卷积输出方差 0.0095，原始特征 0.25），
  按 40 帧块算的统计量随内容摆动，归一化后的尺度跟着晃，DiT 输出整段糊掉：流式 WER 16 %，离线整句却正常。整句统计量跨句只差 1–3 %，
  导出时用 `--norm-stats` 冻成常数即可（图版本 2.0.1，流式 7.6 %）。任何码本模型都适用；诊断链见 MimickingTrain `docs/despeaker-design.md` §13.5。
- 配套规矩：离线 WER 不代表流式；`tools/stream_diag.py --segmented` 在 PyTorch 里按块复现 Rust 会话，与 Lab 吻合，导出前先跑。

## 11. 能量门分不开打字和说话

- 连续敲键盘、敲桌子的响度动态与说话相同，能量门在真实录音上 75–95 % 的块开门，门一开模型就满音量"无中生有"（两套权重都一样）。
  `SileroVad`（`mimic-onnx`，CPU 1 ms/块）键盘 0/144、敲桌 0/179、干净语音 32/32。它只分语音 / 非语音：别人的说话声、部分咳嗽会放行。
- 能量门的地板以第一块电平初始化：剪好的文件开头就是语音 → 地板钉在语音电平、开头几秒静音；录音开头的数字静音 → 地板钉在 −96 dB、
  之后每块只升 0.1–1 dB。离线文件转换不要挂门。
- Silero v5/v6 ONNX 的调用协议：每次 64 点上下文 + 512 点新样本（576），状态 (2,1,128) 带着走；少了上下文，概率恒为 0。

## 12. 扬声器队列：用速率微调吸收时钟漂移，不要靠补静音 / 丢输入

- 麦克风与扬声器不是一个晶振（USB 麦克风对别的扬声器常差 0.1–0.3 %），队列每秒漂几毫秒。按阈值补静音 / 丢输入每约 30 s 剪一刀 80 ms，
  听感是结巴。正确做法：队列误差驱动一级 ±1 % 的变速重采样（P 项 4 s 时间常数 + 慢积分），补 / 丢只在真正卡顿时兜底（MimickingLab 已实现）。
- 单路时 GPU 块间降频让块耗时 p95 比 p50 高 60 ms，余量低于它就欠载；锁频后只差 2 ms，余量可到 50 ms。
- "算法固有延迟"只含右前瞻 + 交叉淡化 + SOLA 搜索（低延迟套 80 ms），块长已在"攒一块"的时间里，别算两遍。

## 13. 麦克风侧

- 系统 / 驱动的自动增益会在一阵响的敲击后把增益压低几秒，表现为"敲完键盘几秒说不出话"，门和模型都无辜。说话电平应在 −25 dBFS 左右，
  −44 dBFS 偏低；关闭"音频增强 / 噪声抑制"。
